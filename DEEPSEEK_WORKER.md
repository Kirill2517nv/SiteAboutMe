# Воркер на DeepSeek – инструкция для оркестратора

Рутина по репозиторию отдаётся дешёвому воркеру, ты остаёшься оркестратором
и отвечаешь за суть. Экономия не в цене токенов, а в том, что содержимое
файлов не попадает в твой контекст: воркер читает их сам, назад приходит
только его отчёт, а правду ты узнаёшь из `git diff`.

## Запуск

```bash
bash scripts/deepseek-worker.sh "текст задания"
bash scripts/deepseek-worker.sh -f "$TEMP/task.txt"   # длинное задание из файла
```

Скрипт – `bash`, не PowerShell: на Windows вызывай его через Bash tool.
Ключ берётся из `DEEPSEEK_API_KEY`, иначе из `~/.deepseek_key` (вне репозитория).
Внутри – headless `claude -p` на Anthropic-совместимом эндпоинте
`https://api.deepseek.com/anthropic`, модель `deepseek-flash[1m]`.

Задание длиннее пары абзацев пиши в файл в скретчпаде и передавай `-f`:
в командной строке кавычки и `$` внутри LaTeX превращаются в отдельную
задачу по экранированию.

Воркеру выданы только `Read Write Edit Glob Grep`. **Bash не выдан намеренно** –
миграции, `manage.py`, тесты, `npm run tw:build` и git делает оркестратор.
Режим `acceptEdits`: воркер правит файлы без спроса, поэтому запускай его
только на чистом дереве или при понимании, что именно он может затронуть.

## Что делегировать

Всё, где решение уже принято, а работа – набрать текст по образцу:

- **контент учебника и разборов ЕГЭ** – `seed_ege_theory_<N>.py`,
  `seed_textbook_block<N>.py`, `seed_spetskurs_<задача>.py`: скелет статьи,
  номер примера, ответ и список ловушек ты задаёшь сам, воркер пишет прозу
  и собирает блоки по соседнему файлу;
- **JSON-фикстуры банков** по `docs/ege-bank-format.md`;
- **единообразные правки по всему дереву** – переименования, замена длинного
  тире, приведение размеров шрифта к шкале кегля, вычитка опечаток;
- **тесты по образцу** – ещё один случай в существующий `TestCase`;
- **докстринги и комментарии** к уже написанному коду.

## Что не делегировать

- **Архитектуру.** Модели, миграции, разделение пулов задач, кто что видит
  (`superuser`-вьюхи, `visibility` блоков), структуру URL. Ошибка тут стоит
  дороже, чем весь выигрыш.
- **Числа, которые попадут ученику.** Ответ задачи ЕГЭ, разложение на степени
  двойки, время норматива. Воркер посчитает и не соврёт – но проверять всё
  равно тебе, поэтому лучше сразу дай ему готовые числа в задании
  и потребуй сверить их вычислением (см. `_check()` в `seed_ege_theory_4.py`
  и `seed_ege_theory_7.py`).
- **Всё, где ошибка не видна в диффе.** Новый Tailwind-класс без
  `npm run tw:build`, правка Alpine-компонента, CodeMirror, виджеты в
  `static/js/textbook-widgets.js`: там проверка – это открыть браузер.

## Как ставить задание

Воркер не знает контекста разговора и не читал CLAUDE.md. В задании должны
быть:

1. **точные пути** – какой файл создать, какой взять образцом;
2. **готовый скелет** – заголовки блоков по порядку и что в каждом;
3. **все числа и ответы**, а не «посчитай сам»;
4. **явный запрет** трогать что-либо ещё;
5. **правила проекта** – их воркер обязан получить в каждом задании, иначе
   напишет по своим привычкам.

Шапка правил, которую стоит копировать в каждое контентное задание:

```
Правила проекта, обязательны:
- язык русский, тире только короткое – (U+2013), длинное — запрещено;
- формулы только LaTeX в $…$; кириллицы и пробелов-разделителей разрядов
  внутри математики быть не должно (не "$16 384$", а "16 384 – это $2^{14}$");
- Markdown, не HTML; внутри бэктиков – код, формулы там не работают;
- объёмы – байт/Кбайт/Мбайт, деление на 1024, единица «КиБ» запрещена;
- склонение по числу – фильтр plural из textbook.templatetags.textbook_tags
  (три формы: ",а,ов"), встроенный pluralize не использовать;
- TODO, заглушек и «здесь можно дополнить» не оставлять.
```

## Проверка результата – обязательная часть схемы

```bash
git status --short && git diff
python manage.py <новая seed-команда>          # контентные задания
python manage.py check_articles --track ege    # или --track textbook
python manage.py test textbook
```

Отчёт воркера читай как заявку, а не как факт: диффом проверяется всё, что
он написал, а `check_articles` и прогон самой команды – то, что он не смог
проверить сам без Bash. Не понравилось – `git checkout -- .` и переформулируй
задание; спорить с воркером дороже, чем перезапустить его.

Отдельно смотри числа: команда с `_check()` упадёт сама, команда без него –
нет, и тогда сверять ответ с фикстурой (`fixtures/bank-<N>.json`,
`fixtures/variant_fipi_demo_2027.json`) придётся тебе.

**`git diff` не покажет новые файлы, а `git checkout -- .` их не откатит.**
Для контентных заданий это основной случай: воркер создаёт файл, и диффом он
проходит мимо ревью целиком. Смотри `git status --short` и читай новый файл
глазами.

Дерево перед запуском должно быть чистым – иначе, если воркер зацепит соседний
файл, его правку не отличить от твоей собственной.
