# Ревизия блока: второй проход по контенту

Инструкция для агента, которому поручили **привести уже наполненный блок учебника в порядок**.
Это не первичное написание уроков (для него — `docs/textbook-lesson-brief.md`), а второй проход:
блок написан, но уроки писались в разное время, разъезжаются по стилю, где-то не хватает
материала, где-то тесты формальные, и у блока нет обязательных задач.

Эталон, на который равняться, — **блок 1 «Введение в информатику и Python»**: он прошёл ревизию
целиком, и все договорённости ниже выведены из этой работы.

---

## 1. Порядок работы

1. **Прочитать блок целиком, прежде чем что-то править.** Открыть `seed_textbook_block<N>.py`
   и прочитать все уроки подряд, как читатель. Не начинать с точечных правок — сначала диагноз.
2. **Сформулировать диагноз списком.** Что разъезжается по структуре, какие фактические ошибки,
   каких тем не хватает, какие вопросы тестов слабые. Показать автору учебника и получить добро.
3. **Править по одному уроку**, после каждого — прогон seed и проверка рендером.
4. **В конце — практикум блока** (раздел 5): задачи придумываются под уже готовый материал.

Правки вносятся только в `seed_*`-команду, не через админку: команда перезапускается и затирает
ручные изменения.

---

## 2. Каркас урока

Каждый урок собирается по одной схеме — это главное, что делает блок цельным.

```
1. «О чём этот урок»       — постановка задачи + что будет разобрано
2. Теория                  — определения, таблицы, примеры кода
   ...
N-1. «Коротко»             — 3–6 пунктов-итогов
```

**«О чём этот урок» — всегда первый блок и всегда с таким заголовком.** Внутри: вход в тему
через предметную задачу и абзац «В этом уроке: …» с перечислением того, что будет разобрано.

**«Коротко» — всегда последний блок.** Маркированный список итогов: определения, ключевые
правила, подводные камни. Это то, к чему ученик вернётся перед контрольной. Без него урок
заканчивается ничем.

### Урок должен быть самодостаточным

Не начинать урок с пересказа предыдущего. Формулировки «в прошлом уроке мы разобрали…»,
«во всех примерах прошлых уроков…» в первом блоке **запрещены**: ученик мог прийти на урок
по прямой ссылке или из поиска.

| Плохо | Хорошо |
|---|---|
| «В прошлом уроке мы выяснили, что информатика — наука о работе с информацией…» | «Компьютер — инструмент удивительно универсальный: одной и той же машиной человек набирает текст, монтирует видео и играет» |
| «Во всех примерах прошлых уроков числа были зашиты в код» | «Программа `print("Привет, мир!")` всегда выводит один и тот же текст» |

Ссылки на соседние темы **внутри** урока допустимы и полезны — но как справка, а не как опора:
«это та же ошибка, что при опечатке в имени функции», «подробно разберём в блоке про строки».

### Блока «Куда движемся дальше» быть не должно

Анонс следующего урока в конце каждой статьи — это шум. Исключение ровно одно: **первый урок
блока** может закончиться блоком «Что нас ждёт в этом блоке» — планом всего блока и упоминанием
практикума. В остальных уроках последний блок — «Коротко».

### Разминка

Разминка (вопрос к бытовому опыту до теории) — приём, а не обязательный элемент. Если она есть,
она живёт **внутри** блока «О чём этот урок», отдельным абзацем с жирным зачином `**Разминка.**`,
а не отдельным блоком с заголовком «Разминка».

## 3. Оформление текста

- **Определения — блочной цитатой**, всегда одинаково:
  `> **Термин** — определение.` Не жирным текстом в абзаце, не курсивом. Одинаково во всех
  уроках блока.
- **Перечисления из 3+ однотипных пунктов с характеристиками — таблицей**, а не списком.
  Хорошо ложатся: сравнения (ОЗУ и внешняя память), справочники операторов, «понятие → пример».
- **Код внутри пояснения — markdown-фенсом** ` ```python ` прямо в `text`-блоке, а не отдельным
  `code`-блоком. Обёртка с кнопкой «Копировать» навешивается JS одинаково на оба варианта
  (`decorateCodeBlocks()`), но объяснение и пример остаются одним смысловым куском.
  Отдельный `code`-блок оставляем для самостоятельных листингов, которые обсуждаются ниже
  по тексту.
- **Заголовки блоков — назывные или вопросительные по теме**, не «сюжетные».
  «Почему 0.1 + 0.2 не равно 0.3» — да. «Строка была рядом всё время» — нет.
- **Краткое описание статьи (`Article.description`) на странице не показывается.** Заполнять
  его можно (используется в админке), но нести смысл он не должен: роль «о чём статья» играет
  первый блок.

### Чего обычно не хватает

Проверить, что в блоке объяснено, а не «подразумевается». В блоке 1 такими дырами были:

- термин используется до того, как введён (`print()` три урока без слова «функция»);
- комментарии `#` в примерах кода нигде не объяснены;
- ошибки (`SyntaxError`, `NameError`, `TypeError`, `ValueError`) вываливаются в примерах, но
  нигде не сказано, что Python при ошибке останавливается и как читать сообщение;
- нет практических подводных камней темы (точность `float`, `NameError` при опечатке в имени).

## 4. Микротесты после уроков

- **4–5 вопросов** на урок. Три — мало для темы, которую разбирали десятью блоками.
- **Минимум один вопрос на чтение кода**: «что выведет эта программа?». В блоке про Python
  тест без единого фрагмента кода — формальность.
- **Минимум один сценарный вопрос**: не «что такое IDE», а «забыли поставить галочку Add Python
  to PATH — что произойдёт?».
- **Плохой вопрос — тот, ответ на который есть в самом вопросе.** «Впишите одним словом: как
  называется наука об общих законах получения, хранения, обработки и передачи информации?» —
  выкинуть.
- **Если тема настолько мала, что вопросы высосаны из пальца — тест не делать вообще.**
- Текстовые ответы: сверка идёт через `Question.check_text_answer()` — регистр не важен, ведущие
  нули отбрасываются, `alternative_answers` учитываются. Синонимы прописывать явно:
  `alternative_answers=['гигиена труда']`, `['цпу', 'cpu']`.

Микротест **ничего не блокирует**: он не влияет на прохождение блока, попыток не ограничено,
баллы копятся между попытками. Его единственная роль — показать ученику цветом, как он ответил
(зелёный — всё верно, жёлтый — половина и больше, красный — меньше половины). Условие «блок
пройден» — практикум.

## 5. Практикум блока — обязательные задачи

**Практикум — это не статья, а страница задач.** Связь: `Section.practicum_quiz` → `quizzes.Quiz`.
Никаких статей-обёрток: ссылки из учебника ведут прямо на страницу теста.

### Состав

**Количество задач не фиксировано — его нужно согласовать с автором учебника.** По одним темам
задач придумывается много, по другим материала хватает на три-четыре осмысленные — и добивать
до круглого числа за счёт однотипных задач хуже, чем сделать короткий практикум.

Порядок такой: разобравшись с материалом блока, предложить автору список задач (номер, название,
что тренирует, тип) и спросить, сколько оставить и что добавить. Только после этого писать код.

Типы задач:

- **на программирование** — `question_type='code'` с автопроверкой по `TestCase`;
- **для письменного решения** — `question_type='text'`, ответ вписывается строкой;
- **устные** — без автопроверки, для разбора с учителем; их можно не делать вовсе.

Для ориентира: в блоке 1 получилось 12 задач на код и 6 письменных — но это следствие того,
что тема даёт много материала на арифметику и ввод-вывод, а не норматив.

Формулировка «на листочке» в интерфейсе не используется — пишем «для письменного решения»,
в условии: «Вычислите письменно, не запуская код».

### Правила составления задач

- **Только пройденный материал.** Если в блоке не было условных операторов и циклов — ни одна
  задача не должна их требовать. Классические «проверка на чётность» и «калькулятор с выбором
  операции» в блок 1 не годятся: обе требуют `if`. Замены на том же материале: сумма цифр
  двузначного числа, перевод минут в часы, среднее с округлением, число задом наперёд —
  всё решается через `//`, `%` и арифметику.
- **Формат ввода-вывода задаётся явно** и повторяется в каждом условии:
  ```
  Ввод: два целых числа, каждое на отдельной строке.
  Вывод: одна строка — частное и остаток через пробел.

  Пример ввода:
  17
  5
  Пример вывода: 3 2
  ```
- **`input()` без текста-подсказки** — данные подаёт проверяющая система, и подсказка попадёт
  в вывод. Напоминание об этом ставится прямо в условие первой задачи практикума: описание
  теста (`Quiz.description`) ученику на странице задач не показывается.
- **Краевые тесты обязательны.** У каждой задачи 2–3 `TestCase`, среди них — те, что ловят
  типовую ошибку: `700 → 7` (ведущие нули исчезают), `3 3 3 → 3.0` (round даёт `.0`),
  `7 // 10 = 0` (частное ноль), отрицательные числа.

### Проверка задач перед сдачей

**Обязательный шаг: прогнать эталонные решения против своих же тест-кейсов.** Это ловит ошибки
в условиях и в ожидаемых ответах. Скрипт: для каждой code-задачи взять эталон, выполнить с
`input_data` из БД, сравнить с `output_data` через `normalize_output()`.

Отдельно прогнать **хотя бы одну задачу через настоящую песочницу** `run_code_in_docker()` —
локальный Python на Windows не воспроизводит поведение контейнера (кодировки, окружение).

### Как это засчитывается

Задача с кодом считается решённой, **только если пройдены все тесты** (`quizzes/tasks.py`).
Раньше было «хотя бы один» — это осталось от задач ЕГЭ и больше не действует.

## 5а. Дедлайн и оценка за блок

Оба параметра настраиваются учителем в админке (`Section`) и не требуют участия агента —
но при ревизии блока о них нужно спросить автора и заполнить.

### Дедлайн (`Section.deadline`)

После указанного момента блок закрывается: **и задачи практикума, и самопроверки уроков**
перестают принимать решения. Ученик по-прежнему может открыть тест и посмотреть свои ответы —
страница переключается в режим просмотра.

Технически: `Section.is_closed` → `textbook.services.quiz_is_locked(quiz)` → проверка в трёх
точках `quizzes/views.py` (`quiz_detail_view`, `finish_quiz_view`, `submit_code_view`). Тесты
вне учебника дедлайном не затрагиваются.

На главной рядом с блоком показывается «до 25.09», после дедлайна — красное «закрыт».

### Оценка (`grade_5_from`, `grade_4_from`, `grade_3_from`)

Учитель задаёт, сколько **задач практикума** нужно решить на каждую оценку. Всё ниже порога
тройки — двойка. Если «Оценка 3» не заполнена, оценка за блок не выставляется вовсе
(`Section.grade_for()` вернёт `None`, кружок не рисуется).

Пример для 18 задач: 5 — от 16, 4 — от 12, 3 — от 8.

Ученик видит оценку в цветном кружке рядом с названием блока: зелёный (5), синий (4),
жёлтый (3), красный (2). Оценка пересчитывается на лету и до дедлайна работает как
предварительная — решил ещё задачу, оценка выросла.

Пороги задаются в задачах практикума, а не в процентах: их число в блоках разное, и учителю
проще думать «десять задач из пятнадцати», чем «67%».

## 6. Статистика для учителя

Появляется автоматически, как только у блока есть `practicum_quiz` и микротесты. Кнопка
«Статистика» в шапке блока видна суперпользователю.

| Метрика | Источник |
|---|---|
| Задачи блока (решено / всего) | уникальные верные `UserAnswer` по `practicum_quiz` |
| Самопроверки (верно / всего) | уникальные верные ответы по всем микротестам блока |
| Статьи (прочитано / всего) | `ArticleProgress.status in (read, mastered)` |
| Чтение | `ArticleProgress.time_spent_seconds` — активное время вкладки |
| Решение | сумма `UserResult.duration` по тестам блока |
| Ошибки | неверные `UserAnswer`, **где ученик реально что-то ответил** |

Последнее важно: при сдаче теста `UserAnswer` создаётся и для вопросов, которых ученик не
касался. Считать их ошибками нельзя — в статистике для этого есть Q-объект `ATTEMPTED`
(`textbook/views.py`).

По клику на число ошибок открывается детализация: сгруппировано по задачам, для каждой — все
неверные попытки с датой, ответом ученика, отправленным кодом и сообщением проверяющей системы,
плюс метка «Решил позже» / «Не решена».

## 7. Технические грабли

Проверено болью, повторять не стоит.

**Django-комментарии `{# … #}` — только в одну строку.** Многострочный комментарий утекает
в HTML видимым текстом; если внутри был тег (`<button>`), браузер отрисует его как настоящий
элемент. Для длинных пояснений — `{% comment %}…{% endcomment %}`. Детектор:

```bash
grep -rn "{#" templates/**/*.html | while IFS=: read -r f n rest; do
  case "$rest" in *"#}"*) ;; *) echo "МНОГОСТРОЧНЫЙ: $f:$n";; esac
done
```

**Tailwind собран заранее — новых классов в нём нет.** `static/css/tailwind.css` не
пересобирается автоматически, поэтому `h-1.5`, `text-[15px]`, `gap-x-6`, `bg-red-600`,
`border-brand-200`, `disabled:bg-*` в разметке просто ничего не сделают (полоска с `h-1.5`
получает нулевую высоту и выглядит как «текст налез на текст»). Перед версткой проверять:

```python
css = open('static/css/tailwind.css', encoding='utf-8').read()
'.' + 'hover:bg-brand-700'.replace(':', '\\:') in css
```

Версия Tailwind — v4: `shrink-0`, а не `flex-shrink-0`. Произвольные размеры безопаснее задавать
инлайн-стилем (`style="width: 22%"`), он работает всегда.

**Хелпер `_self_check()` пересоздаёт вопросы (`replace=True` по умолчанию), но отказывается,
если по тесту уже есть ответы учеников.** Поэтому после ручного тыканья теста в браузере правки
формулировок в seed перестают применяться. Лечится удалением своих попыток:

```python
UserResult.objects.filter(quiz__in=Quiz.objects.filter(is_self_check=True)).delete()
```

**Проверки прогонять в откатываемой транзакции.** Любой тестовый прогон сдачи теста оставляет
`UserResult`/`UserAnswer`, которые ломают следующий пересев (см. выше). Шаблон:

```python
class Rollback(Exception): pass
try:
    with transaction.atomic():
        ...  # решаем тест, проверяем страницы
        raise Rollback
except Rollback:
    print('данные откачены')
```

**Проверять рендером, а не глазами по коду.** После каждой правки шаблона — `Client().get(url)`
и поиск ожидаемого куска в HTML. Django `Client` требует `settings.ALLOWED_HOSTS = ['*']`
в скрипте.

**Windows-консоль портит кириллицу** в выводе `manage.py` — это не ошибка команды. Для читаемого
вывода в своих скриптах: `sys.stdout = io.TextIOWrapper(sys.stdout.buffer, encoding='utf-8')`.

## 8. Чек-лист ревизии блока

Пройти по каждому пункту перед тем, как считать блок готовым.

- [ ] Все уроки начинаются блоком «О чём этот урок» и заканчиваются блоком «Коротко»
- [ ] Ни один урок не начинается с пересказа предыдущего
- [ ] «Куда движемся дальше» нигде нет; план блока — только в первом уроке
- [ ] Все определения оформлены блочной цитатой одинаково
- [ ] Проверены фактические ошибки: числа в заголовках совпадают с содержимым таблиц,
      примеры кода соответствуют тексту рядом
- [ ] В каждом микротесте 4–5 вопросов, есть вопрос на чтение кода и сценарный вопрос
- [ ] Нет вопросов, ответ на которые содержится в формулировке
- [ ] Список задач практикума согласован с автором учебника (количество не нормировано)
- [ ] Создан практикум блока: `Section.practicum_quiz`, только пройденный материал
- [ ] С автором согласованы дедлайн блока и пороги оценок; поля заполнены в админке
- [ ] Эталонные решения прогнаны против всех тест-кейсов, ошибок нет
- [ ] Хотя бы одна задача проверена через `run_code_in_docker()`
- [ ] Все страницы блока и страница задач отдают 200, комментарии в HTML не утекли
- [ ] Тестовые попытки удалены из БД
